# Перенос пользователей и игровых данных

Команда переносит все записи из `auth.users`, `public.games`, `public.rounds`,
`public.teams`, `public.scores` в локальный PostgreSQL. Она не переносит
Supabase sessions, refresh tokens, identities и служебные auth-таблицы.
После переключения все пользователи входят заново своим прежним паролем.

Пробный перенос реальных данных в изолированную локальную базу выполнен:
2 пользователя, 44 игры, 315 раундов, 319 команд, 2328 записей баллов.
Импорт сравнил все переносимые поля до commit; отдельная повторная сверка
также прошла. Источник был прочитан в read-only repeatable-read транзакции
и не изменялся. Резервная копия целевой базы восстановлена в отдельную базу.
Это локальная репетиция, а не переключение production на VPS. Перед
переключением нужен новый окончательный снимок после остановки записи.
Пароли реальных пользователей не запрашивались; совместимость bcrypt и вход
проверены на синтетических аккаунтах.

## Подготовка снимка

1. Получить доступ к полному PostgreSQL-источнику, включая `auth.users`.
   Не использовать выгрузку только игровых таблиц или Supabase REST API.
2. Сделать резервную копию и проверить её восстановление в отдельную базу.
   Хранить копию вне репозитория, Docker-образов и публичных каталогов.
3. Инвентаризировать количество записей, фактические схемы и типы полей,
   способы авторизации и наличие bcrypt-хешей у **всех** аккаунтов. Команда
   останавливается при несовместимом хеше или отсутствии email. Такие аккаунты
   нельзя исключать или менять им пароли без отдельного согласования.
4. Создать изолированную пустую целевую базу и применить Laravel migrations.
   Не использовать рабочую базу старого приложения в качестве целевой.
5. Указать целевое соединение стандартными `DB_*` настройками Laravel.
   В приватном окружении установить `SUPABASE_SOURCE_URL` — PostgreSQL URL
   восстановленного снимка. Не передавать URL аргументом команды, не публиковать
   его в переписке или shell history. Если конфигурация кеширована, обновить
   кеш после изменения окружения.

Пользователю источника достаточно `CONNECT` к базе, `USAGE` на схемы `auth`
и `public`, `SELECT` на перечисленные пять таблиц. Используйте отдельную
учётную запись без прав записи. Источник должен поддерживать обычную
PostgreSQL-транзакцию, поэтому подключайтесь напрямую или через session pooler.
Для финального переноса предпочтителен восстановленный снимок. Read-only
repeatable-read транзакция позволяет также согласованную репетицию с рабочего
источника без его изменения; последующие правки источника в неё не попадут.

## Репетиция

В окружении с заданными подключениями:

```sh
php artisan migrate --force
php artisan supabase:import
php artisan supabase:import --verify-only
```

В Docker выполняйте те же команды внутри контейнера приложения, передав
источник через приватное окружение контейнера. Подключение источника нужно
только для переноса и сверки; обычная работа приложения его не использует.

Импорт:

- отказывается работать с одной и той же исходной и целевой базой;
- требует пустых `users`, `games`, `rounds`, `teams`, `scores`;
- читает один согласованный снимок в `REPEATABLE READ, READ ONLY` транзакции;
- блокирует пять целевых таблиц от конкурентных изменений до завершения;
- проверяет дубликаты email, bcrypt, статусы `draft`/`finished`, владение играми,
  внешние связи и принадлежность команды и раунда одной игре;
- копирует порциями по 500 UUID в порядке users → games → rounds → teams → scores;
- сохраняет UUID, позиции, строки, nullable-поля, дробные баллы, даты игр с
  миллисекундами и даты аккаунтов с микросекундами; временные зоны аккаунтов
  приводятся к UTC без изменения момента времени;
- переносит `encrypted_password` в `password` напрямую, без повторного хеширования,
  `email_confirmed_at` в `email_verified_at`;
- принимает стандартный PHP bcrypt `$2y$` и совместимые Supabase `$2a$`/`$2b$`:
  для последних проверяет полную структуру и допустимый cost, нормализует префикс
  только для определения алгоритма. Исходный хеш не меняется при импорте;
  проверка пароля использует оригинал. После первого успешного входа Laravel
  штатно обновляет хеш до `$2y$`. Проверка алгоритма остаётся включённой;
- сравнивает количество строк и **каждое перенесённое поле по UUID**, включая
  пользователей, прежде чем зафиксировать единственную целевую транзакцию.

Полное совпадение отдельных значений баллов также сохраняет их суммы и
распределения. Команда не отключает внешние ключи, не пропускает ошибочные
строки и не подставляет значения по умолчанию. Ошибка отменяет весь импорт.
Вывод содержит только количества и безопасные описания ошибок — без строк,
хешей, SQL и параметров подключения. Ошибки PostgreSQL возвращают общий отказ,
поскольку текст SQL-исключения может содержать хеш или другие приватные данные.
Для диагностики проверяйте доступ и схему в закрытом окружении.

`--verify-only` ничего не записывает в целевые таблицы, проверяет те же поля
и количества, обнаруживает изменение одной ячейки даже при одинаковом числе
строк. На время проверки SHARE-блокировка предотвращает параллельную запись
в целевые таблицы. Используйте этот режим до открытия приложения на запись:
после штатного редактирования данные закономерно перестанут совпадать со снимком.
Повторный импорт требует новой пустой базы; команда не объединяет данные.

После успешной репетиции владелец самостоятельно проверяет вход в импортированный
аккаунт известным ему паролем, архивные и открытые игры, дробные баллы, порядок
команд и раундов, сохранение и завершение тестовой игры. Пароль не нужно сообщать
в переписке или записывать в логи. Сверьте фактические количества с исходной
инвентаризацией и сохраните безопасный отчёт команды.

## Финальное переключение и откат

1. Остановить запись в старое приложение и дождаться текущих сохранений.
2. Снять окончательный согласованный снимок, сохранить исходную БД и проверить
   резервную копию. Не удалять Supabase-проект.
3. Импортировать снимок в новую пустую production-базу, выполнить `--verify-only`,
   затем проверить вход и чтение игр до открытия публичной записи.
4. Переключить домен, открыть запись только в новом приложении. Старое приложение
   остаётся закрытым для записи. Удалить временный секрет подключения источника.

До открытия записи откат возвращает старое приложение с исходной БД.
После новых записей в монолите сначала остановите запись: возврат старой БД
потеряет изменения, поэтому потребуется согласованный обратный перенос либо
исправление монолита. Автоматического слияния или отката данных команда не делает.

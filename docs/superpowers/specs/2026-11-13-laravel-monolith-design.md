# Перенос Quiz Scoreboard в Laravel-монолит

## Цель и согласованные ограничения

Перенести приложение с Nuxt, Prisma и Supabase на Laravel + Inertia + Vue,
сохранив существующий интерфейс, функциональность, аккаунты и игровые данные.
Размещение — собственный VPS, Docker Compose. После переключения Supabase
не участвует в работе приложения. Изменение дизайна и новые функции не входят
в перенос.

Пользователь сообщает о медленной и нестабильной работе Supabase. Причина
задержек не измерена: новая архитектура убирает эту зависимость, но результат
по скорости необходимо проверить на одинаковых сценариях.

## Рассмотренные варианты

- Laravel + Inertia + Vue: выбран для одного приложения, единой маршрутизации
  и сессионной авторизации с переиспользованием существующих Vue-компонентов.
- Nuxt + Laravel API: меньше изменений клиента, но сохраняет отдельное
  Nuxt-приложение; не соответствует выбранному направлению монолита.
- Laravel + Blade/Livewire: подходит для монолита, но требует существенно
  большего переписывания интерактивной таблицы и её очереди сохранения.

## Архитектура

Браузер обращается к одному HTTPS origin. Nginx отдаёт собранные Vite-ресурсы
и передаёт запросы Laravel через PHP-FPM. Laravel обслуживает Inertia-страницы,
авторизацию и JSON-операции над играми. PostgreSQL работает в той же сети
Docker Compose на VPS.

Один репозиторий и один выпуск приложения. Node используется при сборке
ресурсов; отдельного Node-сервера и Inertia SSR в production нет. Redis,
Octane, WebSocket-сервер и постоянный queue worker для текущих функций
не требуются.

Существующие Vue-компоненты, Tailwind-стили, Pinia, расчёт мест и экспорт
результатов сохраняются. Nuxt-страницы становятся Inertia-страницами;
NuxtLink, navigateTo, middleware, автоимпорты и Nuxt alias заменяются
соответствующими средствами Inertia, Vue и Vite.

## Сохранение поведения

- Вход по email и паролю, регистрация и выход; игры доступны своему владельцу.
- Главная страница со списком открытых и завершённых игр.
- Создание игры с командами и раундами; открытие по существующему UUID.
- Переименование и удаление игры, добавление, переименование и удаление
  команд и раундов. Нельзя удалить последнюю команду или последний раунд.
- Настройки раунда: название, максимальный балл, количество вопросов.
- Дробные баллы, ограничение снизу нулём и сверху максимумом раунда;
  изменение максимума нормализует уже сохранённые баллы.
- Подсчёт суммы, сравнение равных сумм от последнего раунда к первому,
  стабильный порядок при полном равенстве и закрепление строк при вводе.
- Копирование результатов в буфер обмена в текущем TSV-формате.
- Завершение игры после сохранения очереди баллов; завершённую игру
  нельзя редактировать. Текущее разрешение удаления собственной
  завершённой игры сохраняется.
- Маршруты /, /login, /games/new, /games/{id}, /games/{id}/edit сохраняются;
  /game продолжает перенаправлять на /.

Публичная live-таблица, совместное редактирование, offline-режим и новые
способы экспорта не добавляются. Вызов сохранения при скрытии или закрытии
страницы остаётся попыткой сохранения, а не гарантией доставки при закрытии
браузера.

## Сервер и контракт данных

Eloquent-модели User, Game, Team, Round, Score. Контроллеры обслуживают
запросы; Request::validate проверяет входные данные; правила владения и изменения
игры применяются на сервере. Транзакции сохраняют согласованность создания
игры, добавления команд/раундов и пакетной записи баллов.

Существующие /api/games-маршруты и формы JSON-запросов сохраняются, включая
GET /api/games/current и PATCH /api/games/{id}/scores/bulk. Это внутренний
интерфейс монолита; отдельная версия API сейчас не требуется. Создание,
изменение и завершение возвращают объект Game; список возвращает Game[],
удаление — { "ok": true }, текущая игра при отсутствии — null.

Ответ Game сохраняет camelCase, ISO-даты, statusLabel/statusActionLabel,
упорядоченные rounds и teams, scores как словарь roundId -> number.
Сервис snapshot явно формирует этот контракт; стандартная обёртка data
не добавляется. Пагинация и новые фильтры не вводятся в рамках переноса.

Ошибки JSON используют message и, для валидации, errors. Клиентское чтение
statusMessage заменяется чтением нового контракта. Отсутствие входа — 401,
чужая или отсутствующая игра — 404, изменение завершённой игры — 409,
невалидный запрос — 422. Неожиданные серверные ошибки логируются и не
возвращают клиенту SQL, пароли или параметры подключения.

## Автосохранение и производительность

Сохранить существующую очередь Pinia: локальное обновление ячейки, debounce
350 мс, пакет последнего значения каждой ячейки, один активный запрос,
ревизии изменений и сохранение новых правок до следующего запроса.
Медленный ответ не перезаписывает более новый ввод. Ошибка оставляет
несохранённые изменения и видимый статус. Blur/Enter запускают немедленную
отправку. Завершение игры дожидается сохранения очереди.

Пакетный endpoint проверяет принадлежность команд и раундов игре,
нормализует значения и атомарно записывает пакет. Уникальность пары
team_id/round_id сохраняется. Не добавлять запрос к БД на каждую
отрисовываемую ячейку: связанные данные загружаются явно, без N+1.

Начальный вариант работает без кэша игровых данных. Сравнить время
авторизованной загрузки и пакетного сохранения до/после переноса,
зафиксировать время HTTP и запросов БД. Производительность измеряется
на фактическом объёме импортированных данных, а не только на пустой базе.

## Авторизация

Обычная Laravel session authentication и CSRF для одного origin; Sanctum
и JWT для текущего Inertia-монолита не нужны. Состояние пользователя
передаётся Inertia shared props. JSON-запросы передают CSRF-токен и
запрашивают JSON-ответы. Вход и регистрация ограничиваются по частоте.

Сессии хранятся в PostgreSQL. Существующие Supabase-токены и сессии не
переносятся: после переключения пользователи входят заново. Импортировать
состояние подтверждения email, но не вводить новую обязательную проверку
email как часть переноса. Отдельного пользовательского сценария сброса
пароля в текущем приложении нет; его добавление вне scope. Если импорт
обнаружит несовместимые хеши, сначала согласовать способ переноса этих
аккаунтов, не исключать их и не менять пароли молча.

## Данные и импорт

Сохранить PostgreSQL, UUID, таблицы games, rounds, teams, scores, позиции,
статусы, дробные значения и временные метки. Существующие индексы,
каскадные внешние ключи и уникальный индекс scores(team_id, round_id)
переносятся в Laravel migrations. users.id — UUID; games.user_id
ссылается на импортированного пользователя. Laravel timestamps и casts
должны учитывать существующие типы и миллисекундную точность дат.

Supabase auth.users переносится в локальную users: id, email,
encrypted_password -> password, email_confirmed_at -> email_verified_at,
created_at/updated_at. Для новых Laravel-пользователей продолжать UUID.
Не копировать Supabase refresh tokens, identities или служебную auth-схему.

Источник импорта — согласованный снимок исходной PostgreSQL-базы с
доступом к auth.users и четырём игровым таблицам. Импорт выполняется
Artisan-командой в пустую целевую базу после migrations, в порядке
users -> games -> rounds/teams -> scores, с сохранением исходных значений.
Непустая целевая база останавливает импорт; повторная репетиция использует
новую тестовую базу. Ошибки не пропускаются и не заменяются значениями
по умолчанию. На VPS и в репозитории не публикуются дампы или хеши.

До финального переключения на копии проверить наличие всех пользователей,
уникальность email и совместимость bcrypt-хешей с выбранной конфигурацией
Laravel. Вход импортированного аккаунта проверить известным владельцу
паролем, не запрашивая его в переписке и не записывая в логи.

Проверка переноса включает количество записей каждой таблицы, отсутствие
сирот, сравнение полей по UUID, сумм и распределения баллов. Одного
сравнения количества строк недостаточно. Реальные объёмы данных,
дополнительные настройки и объекты исходной БД ещё не проверены;
инвентаризация источника обязательна перед финальным импортом.

## Docker и эксплуатация

Compose-сервисы: nginx, app (PHP-FPM с OPcache), postgres. Production-образы
собираются многостадийно с Composer/npm lock-файлами и включают готовые
Vite-ресурсы. Версии образов фиксируются при реализации; latest не
используется. PostgreSQL не публикует порт наружу и хранит данные в volume.
Контейнеры имеют проверки готовности и политику перезапуска.

HTTPS завершается на reverse proxy VPS перед Nginx приложения. Compose
публикует HTTP приложения на loopback; внешний proxy обеспечивает
сертификат и проксирует HTTPS. Домен, наличие proxy и свободные порты
проверяются при подготовке развёртывания, не нужны для локальной разработки.
Laravel доверяет только настроенному proxy и корректно формирует HTTPS URL.
Это необходимо также для работы clipboard API.

APP_KEY постоянный между выпусками; production env хранится вне git и
образов. APP_DEBUG выключен. Миграции запускаются отдельным шагом выпуска,
а не каждым PHP-процессом. Документация описывает сборку, запуск, миграции,
импорт, резервное копирование и восстановление PostgreSQL. Резервная копия
хранится за пределами volume БД; до переключения проверяется восстановление.

Health endpoint проверяет доступность приложения и БД без раскрытия
параметров подключения. Ошибки PHP/Laravel и Nginx доступны в логах Docker.
Отдельная система мониторинга не добавляется.

## Переключение и откат

1. Сохранить исходную версию в git, реализовать монолит и локальные проверки.
2. Выполнить пробный импорт снимка в изолированную базу и сверку данных.
3. Развернуть монолит на VPS для проверки владельцем до переключения.
4. Остановить запись в старое приложение, дождаться текущих сохранений,
   снять окончательный согласованный снимок и сохранить исходную БД.
5. Импортировать снимок в пустую production-базу и повторить сверку.
6. Проверить вход, чтение архива, сохранение и завершение тестовой игры.
7. Переключить домен на монолит и открыть запись. Старое приложение
   остаётся закрытым для записи; двойная запись не используется.

До открытия записи откат возвращает старое приложение и исходную БД.
После появления новых записей в монолите простой возврат потеряет новые
изменения: сначала остановить запись и перенести изменения обратно либо
исправить монолит. Не обещать автоматический откат данных. Не удалять
Supabase-проект до проверки переноса и сохранения резервной копии.

## Проверки и критерии готовности

- Laravel feature-тесты: вход/выход/регистрация, изоляция владельцев,
  CRUD, ограничения последней команды/раунда, read-only завершённой игры,
  нормализация баллов, атомарность пакетов, формат ответов и импорт.
- Сохранить и адаптировать Vitest-тесты расчёта мест, создания игры,
  загрузки игры и гонок автосохранения.
- Проверить PHP-тесты, TypeScript, production-сборку Vite, Compose config,
  сборку образов и smoke-запросы к контейнерам.
- Ручная проверка текущих экранов, клавиатурного ввода, переходов,
  сохранения при медленном ответе и копирования результатов по HTTPS.
- Playwright не использовать без отдельного запроса пользователя.
- Все исходные аккаунты и игровые записи перенесены и сверены;
  вход импортированного аккаунта работает; текущие функции доступны;
  runtime не обращается к Supabase; инструкция запуска на VPS воспроизводима.

Спецификация описывает согласованное направление и предназначена для
проверки пользователем перед составлением детального плана реализации.
